# character — Codebase index

## Modules
- [`modules/root.md`](modules/root.md) — entry point; assembles `air`/`sff` data into a single `Character` struct, with frame-to-sprite resolution via `ResolveSprite`
- [`modules/air.md`](modules/air.md) — `.air` animation read and write paths: pure-data model (`Animation`, `Frame`, `ClsnBox`), a `Parse` function reading `.air` text into it, a `Serialize` function writing it back out, a `Document`/`ParseDocument` pair for byte-exact, comment-preserving round trips of unmodified files, and a `SpriteResolver` resolving each `Frame`'s sprite reference against sprites loaded via `sff`
- [`modules/sff.md`](modules/sff.md) — `.sff` sprite handling: version-agnostic read-path `Sprite`/`SpriteGroup` structs; v1 read path `ParseV1`/`DecodePCX` (header/sprite table, RLE-compressed PCX pixel decoding); v1 write path `SerializeV1`/`EncodePCX`, completing the v1 read+write cycle; v2 header/sprite/palette-table read path `ParseV2`; v2 read+write pixel handling for raw/PNG sprites (`DecodeV2Sprite`/`EncodeV2Sprite`) plus the full v2 file write path `SerializeV2`, completing the v2 read+write cycle for that format scope; RLE-based v2 formats (decode and encode) still pending
- [`modules/def.md`](modules/def.md) — `.def` character definition read-path vocabulary: pure-data `CharacterInfo` (name, author, and referenced file paths per `.def` section); no parsing or file I/O yet

## Observed patterns
- Root package (`character`) is a thin assembly layer over format-specific sub-packages (`def/`, `sff/`, `air/`, `cns/`) — it now composes `air.Animation`/`sff.SpriteGroup` into `Character` and delegates frame-to-sprite resolution to `air.NewSpriteResolver` rather than reimplementing it; `air/` now has a data model, a read-path parser, a write-path serializer, a format-preserving `Document` type, and a `SpriteResolver` resolving frame references against loaded sprites; `sff/` now has its read-path data model, a complete v1 read+write cycle (`ParseV1`/`DecodePCX`, `SerializeV1`/`EncodePCX`), a v2 header/table read path (`ParseV2`), and a complete v2 read+write cycle for raw/PNG sprite formats (`DecodeV2Sprite`/`EncodeV2Sprite`, `SerializeV2`; RLE-based v2 formats still pending on both sides); `def/` now has its read-path data model (`CharacterInfo`), matching the "data model before parser" order `air`/`sff` followed; `cns/` still doesn't exist.
- Tests are co-located with source as `*_test.go`, one behavior per test function, named `Test<Type>_<Condition>_<Expectation>`.
- Read-path data types (e.g. `air.Animation`/`air.Frame`) store already-resolved values (e.g. per-frame collision boxes) rather than the file format's own authoring shortcuts (e.g. default/override) — parsing concerns stay out of the pure-data model, per an explicit ADR; `air.Parse` performs that resolution while reading, and `air.Serialize` always emits the resolved per-frame boxes rather than reconstructing a default/override split.
- Parsing error handling was deliberately split into its own backlog item after the happy-path parser; `air.Parse` now has a full contract for malformed `.air` content — comment lines are ignored, an empty file is an explicit empty result (not an error), and a malformed header/frame line/negative index/reader failure returns a descriptive, line-numbered error rather than panicking.
- `air.Serialize` always writes fresh text: a semantic round trip through `air.Parse`, not byte-exact preservation of an original file's formatting or comments. Format-preserving round trips instead go through a separate write-path type (`air.Document`) rather than extending the pure-data model or `Parse`/`Serialize` — comment/ordering preservation stays out of the read-only `Animation`/`Frame` vocabulary, per an explicit ADR. `Document` currently only guarantees this for *unmodified* content; it does not yet regenerate output around edits while preserving unrelated comments.
- `air` now depends on `sff` — the first real cross-package dependency in the codebase — for `SpriteResolver`, which resolves a `Frame`'s `(Group, Image)` reference against a `[]sff.SpriteGroup`. The dependency runs one way only (`sff` still depends on nothing), matching CLAUDE.md's architecture diagram, which already documented `.air` as depending on `.sff`. A missing sprite reference is a returned error, never a silently zero-value `Sprite`, per an explicit ADR.
- Version-specific binary parsers/decoders (e.g. `sff.ParseV1`, `sff.ParseV2`, `sff.DecodePCX`, `sff.DecodeV2Sprite`) return a separate, version/encoding-specific low-level type (`V1SpriteTable`/`V1SpriteEntry`, `V2SpriteTable`/`V2SpriteEntry`/`V2PaletteEntry`, `PCXImage`, `V2Image`) rather than populating the shared read-path model directly, when the shared model can't yet hold everything the parser produces (file offsets) or needs (decoded pixel dimensions, palette resolution, per-pixel byte width for indexed vs. direct-color data) — per an explicit ADR, same rationale as the `air.Document` split.
- Their write-path counterparts (`sff.SerializeV1`, `sff.EncodePCX`, `sff.SerializeV2`, `sff.EncodeV2Sprite`) mirror this with their own write-only input types (`V1WriteSprite`, `V2WriteSprite`/`V2WritePalette`), and — unlike `air.Document` — target a semantic round trip (serialize → re-parse → re-decode → compare), not a byte-exact one: `.sff` is binary with no diff-friendliness benefit to preserving an original file's exact layout, per an explicit ADR. `sff.SerializeV2` always writes into the file's single literal data section and `sff.EncodeV2Sprite` only handles the same raw/PNG format scope `sff.DecodeV2Sprite` decodes, per the same ADR pattern.
