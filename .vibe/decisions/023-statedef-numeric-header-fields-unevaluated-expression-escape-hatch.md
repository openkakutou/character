# StateDef's numeric header fields gain a parallel unevaluated-expression escape hatch

**Context:** ADR 011 established that `cns.Controller` stores its parameters as unevaluated key-value data because MUGEN/Ikemen's trigger expression language isn't modeled in this codebase yet. `StateDef`'s own header fields went the other way: `Anim`, `PowerAdd`, `Juggle`, and `SprPriority` are typed as plain `int`, and `Parse` requires `strconv.Atoi` to succeed on their source text, erroring otherwise. Item 032's real-file corpus scan found this is also too strict — real `.cns` files sometimes give these fields a MUGEN trigger expression instead of a literal integer (e.g. `anim = IfElse(ceil(lifemax/2) < life ,181,182)`, `poweradd = ifelse(PrevStateNo = 9000, 0, 20)`), which real engines evaluate at runtime; `cns.Parse` currently rejects the whole file over it. This was the second of item 032's two root causes.

**Decision:** `StateDef` gains one new field, `HeaderExprs map[string]string`, holding the raw, unevaluated source text of any of the four numeric header fields (`anim`, `poweradd`, `juggle`, `sprpriority`) whose value did not parse as a plain integer, keyed by lowercase field name. When a field's text is a literal integer, behavior is unchanged: the typed field (`Anim`, etc.) holds it and no `HeaderExprs` entry is created. When it is not, `Parse` no longer errors — it leaves the typed field at its zero value and records the raw text in `HeaderExprs` instead, mirroring how `Controller.Parameters` already holds unevaluated data alongside `Controller.Type`. `Serialize` writes a field's `HeaderExprs` entry verbatim in place of the typed field's formatted value whenever one is present.

This extends Controller's "unevaluated data" philosophy to these four fields specifically — their real-world need is now demonstrated by the corpus scan — but not further: the boolean header fields (`ctrl`, `facep2`, `hitdefpersist`, `movehitpersist`, `hitcountpersist`) and the string-enum fields (`type`, `movetype`, `physics`) are left as strictly-typed as before. The scan found no real-world evidence of expression syntax on those, and `StateType`/`MoveType`/`PhysicsType` being plain strings already can't fail to parse in the first place. If a future corpus scan finds real files doing the same to a boolean field, the same `HeaderExprs`-map pattern extends to it without a shape change.

**Reason:** A parallel escape-hatch map, rather than changing `Anim`/`PowerAdd`/`Juggle`/`SprPriority`'s own type to a wrapper struct or to `string`, keeps the common case — a literal integer, the overwhelming majority of real files — exactly as simple to read as before for every existing caller, while still giving a caller that needs the expression text somewhere to find it. This is the same trade-off `Controller.Parameters` already makes relative to hypothetical per-controller-type typed fields (ADR 011). It also requires no expression grammar or validation: `Parse` cannot distinguish a "genuinely malformed" numeric value from "a trigger expression it doesn't understand" without building the expression engine ADR 011 explicitly scoped out, so anything that isn't a literal integer is treated as the latter, unconditionally — this is a real, deliberate loosening of what `Parse` rejects (a garbage value like `anim = abc` now parses as an unevaluated expression rather than erroring), accepted because there is no way to tell it apart from a legitimate expression without the evaluator this codebase has repeatedly deferred.

**Rejected alternatives:**
- Change `Anim`/`PowerAdd`/`Juggle`/`SprPriority`'s type from `int` to a wrapper struct (e.g. `IntValue{Literal int; Expr string}`) — rejected: touches every existing read site of these fields for a benefit only the expression case needs, and duplicates the same "typed value or raw fallback" shape four times instead of once.
- Change the fields' type to `string`, storing raw source text unconditionally (literal or not) — rejected: it would make the overwhelmingly common literal-integer case require a caller-side parse on every read, regressing ergonomics on the common path to accommodate the rare one.
- Validate the expression text against a minimal grammar before accepting it, still erroring on genuine garbage — rejected: no expression grammar exists in this codebase (ADR 011 scoped it out), and this item's job was only to establish that real files legitimately hold expressions here, not to build an evaluator able to tell "real expression" apart from "typo" without evaluating either.
