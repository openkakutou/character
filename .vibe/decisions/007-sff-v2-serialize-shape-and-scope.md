# .sff v2 serialization: mirrors the v1 write-path shape, always writes to the literal data section, and only encodes the pixel formats item 011 decodes

**Context:** Item 012 adds the write path for `.sff` v2: turning sprite/palette metadata plus pixel data back into a valid binary file, proving round-trip fidelity against `ParseV2`/`DecodeV2Sprite` (items 010/011). Item 011's decoder only supports `V2FormatRaw` and the PNG formats (`V2FormatPNG8`/`24`/`32`) — `V2FormatRLE8`/`RLE5`/`LZ5` are real but unimplemented, per `.vibe/decisions/006-sff-v2-pixel-decode-shape-and-scope.md`. `V2SpriteEntry` (produced by `ParseV2`) also does not expose whether a sprite's pixel data came from the file's "literal" or "translated" data section — `ParseV2` already resolves that on read into one absolute `Offset`, discarding which section it came from.

**Decision:**
- Add `EncodeV2Sprite(format int, img *V2Image) ([]byte, error)`, the exact inverse of `DecodeV2Sprite`: it supports the same three shapes (`V2FormatRaw`, `V2FormatPNG8/24/32`) and returns a descriptive "unsupported format" error for anything else, including `V2FormatRLE8/RLE5/LZ5`. PNG8 encoding uses a synthetic identity grayscale palette (palette *colors* are never round-tripped by `DecodeV2Sprite`, which only reads back index bytes, so any valid palette works). PNG24 encodes through `image.RGBA` with alpha forced to 255 (opaque, so premultiplication is a no-op and RGB values survive exactly); PNG32 encodes through `image.NRGBA` (straight, non-premultiplied alpha), mirroring `DecodeV2Sprite`'s own use of `color.RGBAModel`/`color.NRGBAModel`.
- Add `V2WriteSprite`/`V2WritePalette`, write-only input types mirroring `V1WriteSprite`'s existing pattern: they carry the same fields as `V2SpriteEntry`/`V2PaletteEntry` minus `Offset`/`Length` (read-time facts, not writer inputs), plus pre-encoded `PixelData`/`ColorData` (e.g. produced by `EncodeV2Sprite`) or an empty slice plus `LinkedIndex` to write a linked (shared-data) entry instead — validated the same way `SerializeV1` validates `V1WriteSprite.LinkedIndex` (in range, not self-referencing).
- Add `SerializeV2(w io.Writer, version [4]byte, sprites []V2WriteSprite, palettes []V2WritePalette) error`. It always writes every sprite's and every palette's data into the file's single literal data section (the on-disk "translated" flag bit is always written 0); the translated data section offset is still written to a valid position (immediately after the literal section, empty) so the header stays well-formed, but nothing ever points into it, since the read-side model this item round-trips against (`V2SpriteEntry`) cannot express "this came from the translated section" as an input in the first place. Like `ParseV2`, only the first `v2HeaderSize` (64) header bytes are written — the remaining comment padding of a real 512-byte v2 header is out of this package's understood scope on both the read and write side.

**Reason:** Keeps the v2 write path's scope symmetric with what item 011 already decodes, for the same reason item 011 itself gave: an under-tested guess at RLE8/RLE5/LZ5's bit-level encoding would risk silently producing corrupt files instead of the honest "unsupported" error this package uses elsewhere for unrecognized/unimplemented input. Reusing the `V1WriteSprite` write-only-type pattern keeps the two format's write paths consistent for a future reader of the codebase, and follows `.vibe/decisions/005-sff-v1-serialize-is-semantic-not-byte-exact-round-trip.md`'s established reasoning that `.sff`, being binary, only needs a semantic (serialize → re-parse → re-decode → compare) round trip, not a byte-exact reproduction of any particular original file's layout choices (which data section a sprite's bytes originally lived in, table ordering, comment padding).

**Rejected alternatives:**
- Adding a "which data section" field to `V2WriteSprite` so callers could still choose translated placement — rejected: `V2SpriteEntry`, the type callers get back from `ParseV2` and would round-trip through this write path, has no field carrying that information (already resolved into an absolute `Offset` on read), so there is no real value to preserve and no way to populate such a field faithfully from a parsed sprite.
- Implementing RLE8/RLE5/LZ5 encoding now for completeness — rejected for the same reason item 011 rejected decoding them: no fixture or acceptance criterion in this item covers them, and an unverified compressed encoder is worse than an honest error.
- Writing the full real 512-byte v2 header (with genuine comment padding) instead of the 64 bytes `ParseV2` understands — rejected: would only add dead padding bytes with no reader in this package to verify their content, for a format this package already scoped down to its needed 64 bytes on the read side.
