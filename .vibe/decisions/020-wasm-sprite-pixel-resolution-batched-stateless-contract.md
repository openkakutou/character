# WASM sprite pixel resolution is a batched, stateless call returning flat straight-alpha RGBA

**Context:** Item 034 adds a second WASM-callable function alongside `OpenKakutouCharacter.load` (item 033/`.vibe/decisions/019`): resolving a sprite's actual decoded pixel colors, not just its metadata, so `character-viewer-web` can render real sprite images. `load`'s JSON contract deliberately left this out (per decision 019's rejected alternatives) pending a real consumer need — that need now exists.

**Decision:**
- **Batched, not per-sprite:** the call is `resolveSprites(sffBytes, requests, overrideBytes)`, where `requests` is an array of `[group, image]` pairs, returning an array of per-sprite results in the same order — not a single-sprite `resolveSprite(sffBytes, group, image, overrideBytes)`. A realistic first consumer (a sprite-sheet browser rendering many thumbnails at once) would otherwise issue one call per sprite, each re-transferring the entire (potentially multi-MB) `sffBytes` buffer across the JS/WASM boundary synchronously on the main thread — visible UI stalls on a large sheet. Batching amortizes that transfer and the sprite-table parse across the whole request instead of once per sprite.
- **Still stateless — no Go-side session/handle:** every call re-parses `sffBytes` fresh; nothing is retained between calls. A handle-based session (returned by `load`, consumed by `resolveSprites`) was considered and rejected: it would eliminate the remaining repeated-parse cost, but introduces a lifecycle this module has nowhere else (when is a handle released? what happens on a JS-side reload without explicit cleanup?) for a cost that batching already addresses for the realistic hot path. Revisit only if profiling a real consumer shows batching insufficient.
- **One override applies to the whole batch:** a single optional `overrideBytes` (an external `.act` file) recolors every sprite in the request, matching a palette-picker UI applying one palette to a visible set — not a per-sprite override list.
- **Return shape per sprite:** `{ pixels: Uint8Array|null, width: number, height: number, error: string|null }`. On error, `pixels` is `null` **and** `width`/`height` are explicitly `0` (never `undefined`), matching `load`'s "exactly one of two fields is non-null" discipline extended to four fields. `pixels` is a flat, row-major RGBA buffer with straight (non-premultiplied) alpha and no padding — `width*height*4` bytes, directly usable as `new ImageData(pixels, width, height)`. This matches how `sff.ResolvePixels` already populates `color.RGBA` (raw decoded bytes copied in directly, never actually premultiplied despite the stdlib type's own documented semantics) — preserved as-is here rather than "corrected," since correcting it is out of this item's scope and would require re-deriving alpha handling error-prone-ly, not free.
- **A sprite lookup miss gets a distinguishable, stable error prefix** (`"sprite not found: ..."`) separate from every other failure (malformed `sffBytes`, corrupt pixel/palette data, oversized declared dimensions). A caller probing `group`/`image` pairs it isn't sure exist (a realistic browsing pattern) needs to tell "expected, keep going" apart from "something is actually broken" without full string-matching every other error message.
- **An explicitly-provided but invalid `overrideBytes` is always an error, never a silent fallback** to the sprite's own palette — including a defined, zero-length `Uint8Array`. Only `undefined`/`null` mean "no override requested." `DecodeExternalPalette`'s existing wrong-size validation already covers this; the WASM glue only needs to route "value present at all" vs. "value absent" correctly, not add new validation.
- **A declared sprite size beyond a sane maximum is a reported error, not an allocation attempt.** `sffBytes` is caller-supplied and can be corrupt or adversarial; nothing before this item exposed pixel decoding directly to a WASM boundary, so nothing before this item needed this guard.

**Reason:** Batching targets the one hot path already identified in this project's own planned features (bulk sprite-sheet display) without taking on session-lifecycle complexity `load` deliberately avoided. The rest of the shape keeps this call's contract exactly as predictable as `load`'s existing one, per external API-design review: unambiguous null/error signaling, a documented pixel byte layout instead of an implied one, and an error taxonomy that survives a real consumer's first "is this sprite just missing" check without freezing an accidental string format later.

**Rejected alternatives:**
- Single-sprite `resolveSprite` call, one sprite per invocation — rejected: cheapest to implement, but the realistic first consumer (sprite-sheet browser) would call it in a tight loop over an entire sheet, re-transferring the full file each time; see Decision.
- Stateful handle returned by `load`, consumed by `resolveSprites` to skip re-parsing `sffBytes` entirely — rejected for now: solves a smaller remaining cost (table re-parse, not the dominant transfer cost) at the price of introducing this module's first resource-lifecycle concern; nothing currently forces this, batching already addresses the realistic bottleneck.
- PNG-encoded return bytes instead of flat RGBA — rejected: adds an encode step in Go and a decode step in JS (async `<img>`/`createImageBitmap` load) for no benefit to a consumer that wants to draw straight into a Canvas; flat RGBA maps directly onto `ImageData` with no extra step.
- A structured error-code field alongside/instead of the human-readable string — rejected as premature: no second consumer or second error category exists yet to justify a taxonomy beyond the one "not found vs. everything else" distinction a real, already-identified consumer needs today.
