# Module: sff

**Role:** MUGEN/Ikemen GO sprite (`.sff`) files. `sprite.go` defines `Sprite` and `SpriteGroup` — the stable, version-agnostic read-path vocabulary a library consumer (editor, engine) works with (no v1/v2-specific fields), since `.sff` has two on-disk versions with different header layouts and pixel encodings that both need to populate the same shape. `load.go` adds `Load`, the version-agnostic top-level entry point that folds a full `.sff` file (v1 or v2, auto-detected from the file's own signature/version bytes) directly into `[]SpriteGroup` — the "later assembly step" the low-level v1/v2 parsers below deliberately left undone. For v1 it decodes each sprite's PCX pixel data (via `DecodePCX`) to recover `Width`/`Height` (absent from the v1 table), resolving linked sprites to their link target first with a cycle/bounds guard, and derives `Sprite.Palette` by incrementing a counter on every non-shared sprite (sharing sprites inherit the current value) since v1's table only records a sharing boolean, not a numeric reference. For v2, every field `Sprite` needs (including an explicit palette bank index) is already in the sprite table, so no pixel data is decoded at all. `v1.go` adds `ParseV1`, a binary reader for the v1 file header and sprite index table: it resolves each sprite's `(Group, Image)` key to the file offset/length of its pixel data, but does not decode that pixel data and does not populate `Sprite`/`SpriteGroup` directly — see the module's design decision below. `pcx.go` adds `DecodePCX`, decoding the RLE-compressed 8-bit indexed PCX pixel data v1 sprites use (the byte range `ParseV1` located) into a pure pixel index buffer plus the dimensions recovered from the PCX data's own embedded header. `pcx_encoder.go` adds `EncodePCX`, the write-path counterpart of `DecodePCX`: RLE-encodes a pixel buffer back into PCX bytes, always as run-length units (never a bare literal), padding an odd width's scanlines to an even `bytesPerLine`. `v1_serializer.go` adds `SerializeV1`, the write-path counterpart of `ParseV1`: writes a full v1 file (header + subheader + pixel data per sprite) from a `V1WriteSprite` slice, deriving the header's group/image counts from the input rather than trusting a caller-supplied count, and validating `LinkedIndex` (in range, not self-referencing) for sprites written without their own pixel data. `v2.go` adds `ParseV2`, a binary reader for the v2 (Ikemen-compatible) file header and its sprite and palette index tables: unlike v1's linked-list subfile chain, v2's tables are flat, fixed-size-record arrays addressed directly by the header's declared table offsets, and each sprite's pixel-data offset is resolved against one of two file-level data section bases (`literal`/`translated`) depending on a per-sprite on-disk flag bit. `ParseV2` locates sprite pixel data and palette bank color data (offset/length) but does not decode either. `v2_decoder.go` adds `DecodeV2Sprite`, the v2 pixel decoder: given a sprite's `Format`/`Width`/`Height`/`ColorDepth` (from a `V2SpriteEntry`) and its raw stored bytes, it decodes `V2FormatRaw` (literal uncompressed indexed data), `V2FormatRLE8` (a run-length-compressed indexed stream: a 4-byte declared-length prefix is skipped unvalidated, then a control byte whose top two bits are `0b01` is a run marker whose low 6 bits give a repeat count for the byte after it, any other byte a literal index, decoding stopping once the declared pixel count is reached), and the PNG formats (`V2FormatPNG8`/`24`/`32`, via the standard library's `image/png`) into a `V2Image`. The remaining RLE-based formats (`V2FormatRLE5`/`LZ5`) and any other format code return a descriptive error instead of being decoded. `v2_encoder.go` adds `EncodeV2Sprite`, the exact inverse of `DecodeV2Sprite`, encoding a `V2Image` back into `V2FormatRaw` or PNG-encoded bytes for the same three PNG formats; the RLE-based formats return the same kind of descriptive error on encode. `v2_serializer.go` adds `SerializeV2`, the write-path counterpart of `ParseV2`: writes a full v2 file (header + sprite table + palette table + a single literal-section data blob) from `V2WriteSprite`/`V2WritePalette` slices, validating `LinkedIndex` (in range, not self-referencing) for both sprites and palette banks written without their own data — completing the v2 read+write cycle for the raw/PNG format scope. `palette.go` adds palette index-to-RGBA resolution, an explicit opt-in step kept separate from `PCXImage`/`V2Image`/`Sprite`: `ResolvePixels` turns a decoded index buffer into a row-major `[]color.RGBA` buffer against a resolved `Palette` (`[256]color.RGBA`), applying one of two `AlphaRule`s (`AlphaForceTransparentAtIndexZero` for PCX/PNG8-decoded sprites, `AlphaLiteral` for RLE8/LZ5-decoded sprites) to determine index 0's alpha. Getting that `Palette` is version-specific: `DecodeV1Palette` decodes a v1 sprite's raw 768-byte embedded RGB block (always opaque) and `ResolveV1Palette` locates it — walking backward from a sprite index to the nearest sprite whose `SharedPalette` is false and reading its block from `Offset+Length` (confirmed empirically against the real fixtures that a v1 sprite's declared pixel-data `Length` does not include this trailing block); `DecodeV2Palette` decodes a v2 palette bank's already-RGBA raw color data and `ResolveV2Palette` follows a zero-length bank's `LinkedIndex` chain to the bank whose colors it reuses, cycle/bounds-guarded like v1's linked-sprite resolution.

**Design decision:** `ParseV1`'s output is a separate low-level type (`V1SpriteTable`/`V1SpriteEntry`), not the public `Sprite`/`SpriteGroup` model — it carries a file offset/length that model has no field for, and lacks `Width`/`Height`, only knowable once pixel data is decoded. See `.vibe/decisions/004-sff-v1-table-is-a-separate-low-level-type.md`. `DecodePCX` follows the same pattern: it returns a `PCXImage` (pixel buffer + dimensions), not a populated `Sprite` — `Width`/`Height` resolution into `Sprite` is `Load`'s job, and resolving those same indices into actual on-screen colors against a palette is `palette.go`'s further opt-in step (see below). On the write side, `SerializeV1` takes its own write-only input type (`V1WriteSprite`) rather than reusing `V1SpriteEntry` (whose `Offset`/`Length` are read-time facts, not writer inputs), and — unlike `air`'s `Document` type — does not attempt a byte-exact round trip of an original file: `.sff` is binary with no diff-friendliness benefit to preserving one, so round-trip fidelity is verified semantically (serialize → re-parse → re-decode → compare). See `.vibe/decisions/005-sff-v1-serialize-is-semantic-not-byte-exact-round-trip.md`. `ParseV2` follows the same low-level-type pattern as `ParseV1` (`V2SpriteTable`/`V2SpriteEntry`/`V2PaletteEntry`, not `Sprite`/`SpriteGroup`), for the same reasons, plus a v2-specific one: v2 additionally needs a palette bank table (`V2PaletteEntry`), which v1's simpler per-sprite/shared palette flag has no equivalent of. `DecodeV2Sprite` returns its own `V2Image` rather than reusing `PCXImage`, since v2 sprites can be direct-color (PNG24/32, no palette involved) and not just indexed like every v1 sprite; `V2Image.BytesPerPixel` tracks which case applies. Raw, RLE8, and PNG-encoded formats are decoded — the remaining, less common RLE-based formats (LZ5, RLE5) return a descriptive "unsupported format" error rather than being guessed at. See `.vibe/decisions/006-sff-v2-pixel-decode-shape-and-scope.md`. `SerializeV2`/`EncodeV2Sprite` mirror `SerializeV1`/`EncodePCX`'s write-only-type and semantic-round-trip pattern (`V2WriteSprite`/`V2WritePalette`, not `V2SpriteEntry`/`V2PaletteEntry` reused), always write into the file's single literal data section (v2's read-side model has no field recording which of the two sections a sprite's data came from, so nothing meaningful to preserve there), and only encode the raw/PNG format scope `DecodeV2Sprite` originally decoded — its encode scope has not grown alongside `DecodeV2Sprite`'s later RLE8 decode support, so RLE8 (like LZ5/RLE5) stays a descriptive "unsupported format" error on write. See `.vibe/decisions/007-sff-v2-serialize-shape-and-scope.md`. `Load` is where that deferred "later assembly step" finally happens: it dispatches to `ParseV1`+`DecodePCX` or `ParseV2` (v2 needs no decoder — its table already carries `Width`/`Height`/`PaletteIndex`) and folds the result into `Sprite`/`SpriteGroup`, deriving v1's numeric `Palette` from its boolean sharing flag via a running counter since no numeric palette reference exists on disk for that version. See `.vibe/decisions/010-def-loader-assembles-character-from-referenced-files.md`. `ResolvePixels`/`Palette` are kept separate from `PCXImage`/`V2Image`/`Sprite` for the same "pure-data read-path type carries no resolution logic" reason as `DecodePCX`/`Load`; the v1/v2-specific `Palette` getters are their own low-level-vs-resolve split (`DecodeV1Palette`/`DecodeV2Palette` decode raw bytes already in hand, `ResolveV1Palette`/`ResolveV2Palette` locate those bytes against a table + `io.ReaderAt`, mirroring `DecodePCX`/`Load`). See `.vibe/decisions/014-palette-resolution-api-shape.md`.
